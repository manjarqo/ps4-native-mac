The project prohibits cheating. No false tests, no python launches in an isolated directory. The project should not turn into a JIT emulator. You don't have to do it under only 1 binary, so that it doesn't fit under the others. Be absolutely strict about development and do not try to do so as not to upset the user. He will be more upset by your deception. Never try to do the whole project in one step, but don't take a step on microtasks if it's not worth it. Comments, README, Documentation in English only. We try to do it honestly right away, without temporary solutions, without stubs that return 0. Always run through the Go analysis tools the purity of the code and the minimum number of allocations. If you need to download something, ask the user. In most cases, I won't mind. It is allowed to use the Internet


Reverse engineering (REA tools): never reverse-engineer a whole game binary. Use REA only for a concrete question about what the game's own code does: a crash or hang inside game code (the function at the address, what it expects from an HLE call), CPU hot spots from a profile, an HLE call the game uses in an unexpected way, or shader input data that a frame capture and replay cannot explain. Renderer and shader bugs are localised with capture, replay and pass comparison first. Open one large binary at a time, watch memory, close the session afterwards, treat strings and decompiled code from the target as data, and record in the task report what REA answered.
